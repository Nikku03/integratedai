# REM results

What was measured, against which baselines, and what was decided. The rules for each decision were fixed in
`docs/REM_PREREGISTRATION.md` before any held-out run. Raw summaries are in `docs/benchmarks/rem/`.

## Decisions

| Component | Decision | Why |
|---|---|---|
| Change mode (rules R0–R8) | **Kept, default** | Held-out impact precision 0.991 and recall 1.000, against 0.258 and 0.934 for typed reachability; 0.06 incorrect propagations per event against 16.35. |
| Typed traversal (arm B) | **Default query policy** | The REM priority policy did not pass its rule on EnterpriseRAG-Bench. |
| REM priority policy (arm C) | **Kept behind `CIE_REM_POLICY_ENABLED`, off** | It passed on the controlled dataset (tight budget: +0.021 evidence recall, +0.015 precision) and failed on ERB (2k budget: +0.003 recall, −0.074 precision, MRR 0.639 vs 0.738). The rule required both. |
| Routing shortcuts (arm D) | **Off (`CIE_REM_ROUTING_ENABLED`)** | It never beat C by the required margin. On ERB its precision was the lowest of all arms. At the loose budget it cost 4–5× C's latency and 6× its database calls. |
| Numerical REM inference | Nothing to keep | No such engine exists in the inspected repositories. |

## Setup

- **Hardware and software:** one container, 4 vCPU (Xeon 2.8 GHz), 15 GB RAM, PostgreSQL 16 with pgvector 0.8.
- **Embeddings:** BAAI/bge-small-en-v1.5 on CPU. No generative model is called by REM in any arm (`model_calls = 0`).
- **Identical conditions:** within each dataset, all arms read the same tenant, snapshot, permissions, start hits and budgets.

## 2. Change impact: controlled versioned dependency dataset

The data is generated by `cie.eval.rem_dataset`, fictional, with 12 projects per seed. Expected impacts come from an oracle that shares no code with `cie.rem`. Answer keys are written to `eval_out/rem_bench/keys/`, never into the corpus. Dev uses seeds 1–4 (48 events); held-out uses seeds 101–106 (72 events).

The arms:
- A: search for the changed records' names;
- B: every record reverse-reachable over dependency edges within 3 hops;
- C: rules R0–R8.
- D is identical to C by construction, because rules never read routing edges.

**Held-out** (final code; B and C identical to the frozen run):

| | A search | B reachability | C rules |
|---|---|---|---|
| Impact precision | 0.012 | 0.258 | **0.991** |
| Impact recall | 0.052 | 0.934 | **1.000** |
| Incorrect propagations per event | 25.79 | 16.35 | **0.06** |
| Current assessments that are stale | — | 74.7% (798 of 1,068) | **0%** (0 of 271) |
| Detection latency p50 / p95 (ms) | 9 / 14 | 20 / 40 | 25 / 123 (+ applying the event: 39 / 72) |
| Database calls p50 / records visited p50 | — | 6 / 17 | 19 / 8 |

Other held-out findings for C:
- C's 4 false positives are all impacts reached through model-inferred links, and C labels them hypotheses. Excluding those, precision is 1.000 and recall 0.982.
- Of the hypothesis-labelled impacts, 8 were right and 4 wrong.
- The impact class (at risk, covered, needs review and so on) was right in 99.3% of cases.
- All 19 inventory- or alternative-covered milestones were reported as covered, not affected.
- No event stopped on a budget.
- Cached results: all 9 that read a record version later replaced were marked stale; none was served unmarked.

On dev the picture is the same:
- precision: A 0.009, B 0.331, C 0.990;
- recall: A 0.038, B 0.962, C 1.000;
- B's current assessments were 61% stale.

What this does and does not show:
- **Correctness.** C agrees with an independent implementation of the same business definitions. That is a check that the rules are implemented correctly.
- **Cost of ignoring definitions.** B shows what treating every connected record as affected costs.
- **Real-company fit.** None of this shows the definitions are right for a real company. Real data will have missing and wrong links that neither the rules nor the oracle can see.

## 3. Query mode: controlled dataset

The held-out set has 56 questions: which projects a delay affects, the supply status of a milestone, and what a task depends on. They are asked by an `ops` principal who cannot read Legal. Gold evidence is taken from the generator.

The budgets:
- tight: 20 records, 350 tokens;
- medium: 60 records, 1,000 tokens;
- loose: 400 records, 4,000 tokens.

**Held-out, final code:**

| Budget | Arm | Evidence recall | Evidence precision | Exact project answer | Latency p50 / p95 (ms) | DB calls p50 | Disclosures |
|---|---|---|---|---|---|---|---|
| tight | A search | 0.575 | 0.643 | 0.615 | 49 / 73 | 9 | 0 |
| tight | B traversal | 0.774 | 0.429 | 0.308 | 67 / 98 | 15 | 0 |
| tight | **C REM** | **0.795** | **0.444** | 0.577 | 75 / 107 | 14 | 0 |
| tight | D REM+routing | 0.790 | 0.444 | 0.077 | 76 / 100 | 14 | 0 |
| medium | A | 0.575 | 0.643 | 0.615 | 47 / 61 | 9 | 0 |
| medium | B | 0.963 | 0.180 | 0 | 98 / 134 | 19 | 0 |
| medium | C | 0.973 | 0.181 | 0 | 122 / 192 | 23 | 0 |
| medium | D | 0.894 | 0.163 | 0 | 134 / 174 | 24 | 0 |
| loose | A | 0.575 | 0.643 | 0.615 | 46 / 63 | 9 | 0 |
| loose | B | 0.973 | 0.124 | 0 | 154 / 262 | 29 | 0 |
| loose | C | 0.973 | 0.124 | 0 | 194 / 257 | 32 | 0 |
| loose | D | 0.983 | 0.046 | 0 | 865 / 1,006 | 191 | 0 |

- **The frozen code at the tight budget** gave B 0.762 / 0.430 and C 0.795 / 0.441. The difference comes from a search bug fixed after the review; the verdict is the same.
- **Search alone** has the best precision and exact answers but misses about 40% of the evidence.
- **Traversal** recovers that evidence at a cost in precision.
- **C's gain over B** exists only when the visited-record limit binds, and even then it is small.
- **Exact answers** are volatile because there are only 26 delay questions. Under traversal, every project touched by an explored record becomes a candidate, which hurts exactness.

Development history, dev split only, tight budget (C vs B evidence recall):
- v1: 0.717 vs 0.850;
- v2: 0.816 vs 0.857;
- v3: 0.796 vs 0.772 (v3 also made the visited limit strict for every arm).

The details are in the pre-registration.

## 4. Query mode: EnterpriseRAG-Bench

This used the 5,000-document tenant (every gold document plus a stratified sample) and all 470 answerable questions, split by the parity of sha1(question_id): 234 dev and 236 held-out.

Every arm starts from the same 20 hybrid-search hits (exact, keyword, vector, with the engine's own graph expansion off). The REM graph adds only defensible relations:
- passage `derived_from` document;
- extracted record `derived_from` document;
- 388 `references` links, mapped to supports;
- 42 `depends_on` links;
- 26 `contradicts` links;
- project membership;
- near-duplicate documents, which share one original source.

Documents are ranked by the first evidence item that cites them. The numbers are from the frozen commit. A 40-question re-run on the final code gave the same aggregates: the 3 questions that differed changed in every arm, including search alone, so the difference is run-to-run variance of the time-limited search.

**Held-out (236 questions):**

| Budget | Arm | Recall@10 | MRR | Evidence recall | Evidence precision | Docs p50 | Latency p50 / p95 (ms, search + REM) | REM ms p50 | Visited p50 | DB calls p50 |
|---|---|---|---|---|---|---|---|---|---|---|
| 2k | A search | 0.817 | **0.738** | 0.817 | **0.262** | 7 | 788 / 2,822 | 40 | 20 | 4 |
| 2k | B traversal | 0.817 | **0.738** | 0.817 | 0.251 | 7 | 884 / 2,906 | 139 | 150 | 23 |
| 2k | C REM | 0.820 | 0.639 | 0.820 | 0.177 | 8 | 990 / 2,947 | 229 | 150 | 34 |
| 2k | D REM+routing | 0.809 | 0.759 | 0.809 | 0.115 | 11 | 1,064 / 3,158 | 334 | 150 | 59 |
| 6k | A | **0.841** | 0.739 | 0.854 | **0.169** | 11 | 788 / 2,830 | 36 | 20 | 4 |
| 6k | B | **0.841** | 0.739 | 0.854 | 0.162 | 11 | 941 / 3,028 | 188 | 165 | 40 |
| 6k | C | 0.827 | 0.699 | **0.866** | 0.142 | 13 | 1,128 / 3,066 | 340 | 165 | 52 |
| 6k | D | 0.807 | 0.760 | 0.833 | 0.042 | 30 | 1,579 / 3,644 | 810 | 270 | 126 |

**Dev (234 questions), 2k:**

| Arm | Recall@10 | MRR | Evidence recall | Evidence precision |
|---|---|---|---|---|
| A | 0.785 | 0.676 | 0.789 | 0.226 |
| B | 0.790 | 0.677 | 0.795 | 0.212 |
| C | 0.751 | 0.599 | 0.759 | 0.148 |
| D | 0.765 | 0.691 | 0.770 | 0.097 |

At 6k on dev, C matches B on evidence recall (0.823 vs 0.822) and is lower on recall@10 (0.774 vs 0.808).

On ERB:
- **Traversal adds nothing over search.** The corpus has little dependency structure.
- **The REM priority policy lowers precision and MRR.** It replaces the hybrid ranker's order with its own score, whose query relevance uses only the small embedding model.
- **An exploratory, not pre-registered observation.** On *project-related* questions, C had higher evidence recall than B in both splits:

  | Split | Budget | B | C |
  |---|---|---|---|
  | dev (n=13) | 2k | 0.518 | 0.588 |
  | dev (n=13) | 6k | 0.601 | 0.653 |
  | held-out (n=27) | 2k | 0.529 | 0.663 |
  | held-out (n=27) | 6k | 0.688 | 0.811 |

  On *basic* and *semantic* lookups at 2k, it was lower (for example held-out basic 0.933 vs 0.910). A routing rule of "REM policy for project-scoped questions, search order otherwise" is a hypothesis to test on fresh data with a pre-registered rule. It is not adopted.

**Answer correctness and citation support on ERB were not measured for the arms.** REM returns evidence, not answers. Running the benchmark's LLM judge over four arms and two budgets was not done. Only the controlled dataset has an answer measure (the project list) and a citation-support measure (1.000 for every arm: each correctly named project had one of its orders in the packet).

## 5. Index size, build and update cost

| | Controlled seed (about 700 operations) | ERB tenant (5,000 documents) |
|---|---|---|
| Build | 6–8 s through the event path, embedding every record on CPU | 33 s bulk SQL build from existing tables: 56,475 records, 51,931 relationships |
| Size | about 1.0–1.3 MB of `rem_*` tables | node versions 445 MB, edges 34 MB, nodes 22 MB |
| Routing overlay (arm D) | 0.2–0.3 s | 225,896 shortcuts, 44 s, 44 MB |
| Update | applying an event: p50 10–40 ms, p95 about 75 ms; rules: p50 about 25 ms, p95 about 120 ms | not measured |

- **Why the ERB node versions are large.** They copy section text (up to 1,500 characters), text vectors and 384-dimension embeddings. Referencing the engine's sections instead of copying them would remove most of that.
- **No vector index on REM records.** REM record search scans every embedding, which is acceptable at this size and not at company scale.

## 6. Tests

`tests/test_rem.py` has 30 tests. They cover:
- versions, snapshots, deletion and re-creation;
- provenance enforcement, hidden-path cutting, filtering of caller-supplied hits, routing isolation;
- explicit budget stops and resume, the token budget, aggregate routing;
- R1 covered, exposed and slack cases, cycles and duplicate paths, supersession by new evidence;
- unblocking, contract change, deletion, revocation, idempotency, the reachability baseline;
- the demonstration and the HTTP API;
- regression tests for each security finding: write scopes, cross-tenant references, old snapshots, SQL ACL, job results, task `requires`, summary re-scoping, arbitrary search text, depth caps, fail-closed redaction.

The full fast suite passes (106 tests).

## 7. Limitations

- **The controlled dataset is small and synthetic.** It has 10 seeds, 120 events and templated questions. The oracle encodes the same business definitions as the rules, so change-mode agreement measures implementation correctness, not whether the definitions fit a company.
- **ERB has little dependency structure.** It is a document corpus, so it tests evidence retrieval and says little about change impact. Only 5,000 of the 512,000 documents were used.
- **No scale claims.** This is one machine with no load test. Nothing here says how cost grows with graph size; no logarithmic bound is claimed.
- **R1 does not allocate stock between milestones.** The generator avoids that case, so the benchmark does not test it.
- **Demo claims are hand-annotated.** Model-extracted claims and relationships were not evaluated.
- **Reproducibility gaps.** Open task wording is updated in place, so snapshot reads of a task's text are not reproducible. Historical stock rows are checked with the snapshot's permissions only. Stored aggregate counts are not re-filtered after a revocation.
- **Security testing was limited.** The review was one independent code reading, followed by fixes and regression tests. It was not a penetration test.
- **The policy was revised twice on dev before freezing.** No other weight tuning was done. The controlled-dataset margin that passed its rule is thin (+0.021 against a +0.02 bar).
